For most websites in Nepal the answer is **eSewa and Khalti first**, then NPS OnePG or Fonepay when you need bank customers too. Both wallets have a fully public sandbox, and the server code for both follows one pattern: sign on the server, let the gateway's status API decide, and fulfil each order exactly once.

There are eight gateways a developer can integrate today: the eSewa and Khalti wallets, Fonepay and NEPALPAY QR for bank QR, connectIPS for direct bank debit, CyberSource for cards through a Nepali bank, NPS OnePG as an aggregator over about 29 banks plus wallets, and IME Pay for existing merchants. This page compares them, explains how to choose, and links to a step-by-step guide for each.

The facts here come from the provider references in my open source [Nepal Payments](/docs/) project, which I checked in November 2026 against provider docs, official plugins and SDKs, and sandbox calls wherever a public sandbox exists.

## Payment gateways in Nepal compared

| Gateway | Type | Signing / auth | How payment is confirmed | Public sandbox | Mobile flow |
|---|---|---|---|---|---|
| **eSewa** | Wallet | HMAC-SHA256, base64 | Status API, called with the total you stored | Yes: `EPAYTEST` credentials are published | Intent app-to-app (eSewa's recommendation; its SDKs are deprecated) or ePay in a WebView |
| **Khalti** | Wallet | `Authorization: Key <secret>` header | Lookup by the `pidx` you stored | Yes: self signup at test-admin.khalti.com, wallet payments only | Native SDKs (Flutter, Android, iOS) or WebView |
| **Fonepay** | Bank QR | HMAC-SHA512 `DV`, hex | txnVerification (or the legacy verification) | Partial: dev sample `NBQM` covers the redirect only | WebView; Dynamic QR pushes status over a WebSocket |
| **NEPALPAY QR** | Bank QR (NCHL) | RSA-SHA256 `token` with your NPI `.pfx`, plus Basic auth | Transaction report by the `validationTraceId` you stored | No: credentials through your bank or NCHL | No SDK: the app shows `qrImage` or renders `qrString`, and the payer scans it with a bank app |
| **connectIPS** | Bank debit (NCHL) | RSA-SHA256 `TOKEN` with your creditor `.pfx` | `validatetxn` with Basic auth | No: test accounts from connectIPS support | WebView (with cookies enabled) |
| **CyberSource** | Cards via Nepali banks | HMAC-SHA256 over every signed field, base64 | Signed response POST (no simple status API) | No: credentials come from your bank; test cards are public | WebView, or the system browser for 3-D Secure |
| **NPS OnePG** | Aggregator | HMAC-SHA512, hex, plus Basic auth | `CheckTransactionStatus` | No: credentials from NPS onboarding | WebView |
| **IME Pay** | Wallet (merged into Khalti) | Basic auth, no HMAC, unsigned callbacks | `Recheck`, `ResponseCode` 0 = paid | No: from the merchant team | WebView (its SDK puts API credentials in the app) |

Three columns drive the planning. **Signing** tells you which secret lives on your server. **Confirmation** tells you which server-to-server call decides that money moved. **Sandbox** tells you whether you can start coding today or have to wait for a bank.

### eSewa vs Khalti

The two get compared most, so here is the difference in one place:

| | eSewa (ePay v2) | Khalti (KPG-2) |
|---|---|---|
| Starting a payment | Your server signs a form; the browser posts it to eSewa | Your server calls `initiate` and redirects to the returned `payment_url` |
| Amount format | Rupee string, signed exactly as posted | Integer paisa, minimum Rs 10 |
| Confirming | Status API with your stored total; `COMPLETE` = paid | Lookup with your stored `pidx`; `Completed` = paid |
| Refunds | No API; refunds show up in the status API | Merchant refund API or the dashboard |
| Mobile | Intent deeplink, server-booked | Official Flutter, Android and iOS SDKs |

Neither one sends a webhook, so both need the reconciliation job described below.

### Smaller gateways

These have no adapter in my project, and most have little public documentation:

- **Himalayan Bank (HBL)** runs its card gateway on 2C2P PACO. Requests are a JWS (PS256) wrapped in a JWE, so you need bank-issued keys plus two RSA-4096 key pairs you generate before you can test. Status comes from `Inquiry/transactionStatus`. One package claims HBL uses Mastercard MPGS instead, so confirm the product with the bank.
- **Prabhu Pay** has no public docs. The only source is a community WordPress plugin (`Initiate`, then `CheckStatus` where `status == "00"` means success). Treat it as unverified and get the spec from Prabhu Pay.
- **Moru** has official docs, a web SDK and a Flutter package. The SDK's `onSuccess` is not proof: call `check-payment` from your server and require `state == "Completed"` with a matching amount.
- **CellPay** ships Android and Flutter SDKs only. There is no public server-side verification API, so ask CellPay for one before going live.
- **Namaste Pay** (MoCo) has nothing public. Specs come from its business team.

NPS already routes to HBL Card Checkout, Khalti, MORU, MyPay, Hamro Pay and about 29 banks, so integrate these directly only when you need your own contract with them. Details are in [other gateways](/docs/providers/others/).

## How to choose a payment gateway in Nepal

Pick by who your customers are and what they pay with.

- **Wallets (eSewa, Khalti).** Start here for a consumer website or app. Both have a public sandbox and a mobile path that switches to the wallet app. Integrate both: the server side is the same, so the second one is one new module.
- **Bank QR (Fonepay, NEPALPAY QR).** Payers scan with their bank app. It fits shops and restaurants too, since a dynamic QR shows a code on a screen. Fonepay pushes the result over a WebSocket. NEPALPAY QR is NCHL's national scheme: any NEPALPAY QR enabled bank or wallet can pay it, and your server polls the transaction report (or listens on NCHL's WebSocket) until the payment shows up.
- **Direct bank debit (connectIPS).** The payer logs in through NCHL, picks a bank account and approves the debit with an OTP. It reaches customers who have a bank account but no wallet. Onboarding runs through your bank and NCHL, so plan for the wait.
- **Cards (CyberSource, HBL).** Only through a Nepali acquiring bank. Secure Acceptance credentials a bank already issued still work, but CyberSource is sunsetting Secure Acceptance and REST HTTP Signature auth must move to JWT by March 2027. For a new build, ask the bank for Unified Checkout and REST credentials.
- **Aggregator (NPS OnePG).** One integration reaches about 29 banks' mobile and e-banking, bank card checkouts and several wallets. Choose it when "every bank" matters more than a native wallet experience.

My default for a new site: eSewa and Khalti first, then NPS or Fonepay for bank coverage. Skip IME Pay for new builds, since Khalti now reaches its users.

## How to get a merchant account

Every gateway needs merchant onboarding before it issues live keys.

| Gateway | Where production credentials come from |
|---|---|
| eSewa | Merchant onboarding at [merchant.esewa.com.np](https://merchant.esewa.com.np). eSewa issues a live `product_code` and secret key, plus an Intent access key and production host for mobile. |
| Khalti | Live keys from admin.khalti.com. Complete KYC and the contract, otherwise live payments are capped at NPR 200. |
| Fonepay | Your acquiring bank and Fonepay onboarding: the PID (merchant code), secret key and a merchant panel login, which txnVerification and Dynamic QR need. |
| NEPALPAY QR | Enrol through your acquiring bank, or email businesssupport@nchl.com.np for dynamic QR integration. NCHL issues the acquirer id, merchant id, merchant category code, an NPI user and a signing `.pfx`. |
| connectIPS | Enrol through your bank (KYC, creditor account). The bank lists you with NCHL, and NCHL emails `MERCHANTID`, `APPID`, `APPNAME`, an app password and the creditor `.pfx`. Success and failure URLs are registered with NCHL. |
| CyberSource | Your acquiring bank issues the Secure Acceptance profile ID, access key and secret key. Keys expire after two years. |
| NPS OnePG | NPS onboarding gives a developer guidelines PDF, `MerchantId`, `MerchantName`, API username and password, and `SecretKey`. The Notification URL is configured with NPS at onboarding. |
| IME Pay | Existing merchants only, through the Khalti by IME merchant team. Port 7979 must be reachable outbound, and IME may need to whitelist your server IP. |

<Note title="Fees and settlement">
  None of the specs I worked from publish fees or settlement times, so I don't list them. NPS exposes <code>GetServiceCharge</code> and connectIPS returns <code>chargeAmt</code> per transaction, so read charges from those APIs rather than hardcoding them.
</Note>

## How online payments work with any Nepali gateway

The wire formats differ. Everything around them is the same, and that is where most production bugs live: duplicate callbacks, buyers closing the tab mid-payment, flaky provider APIs and tampered redirect URLs. Every integration needs the same five parts.

<ol class="steps">
  <li><strong>Sign on the server.</strong> eSewa, Fonepay, NEPALPAY QR, connectIPS, CyberSource and NPS sign requests; Khalti and IME Pay use API keys. All of them stay in backend env vars or a secret manager, never in a web bundle or mobile app. The browser or app sends only an order id and a gateway name, and the server reads the amount from the database.</li>
  <li><strong>Create a payment attempt per click.</strong> Every Pay click gets its own row with a fresh id, the amount in integer paisa, and a status that starts at <code>initiated</code>. Gateways reject or misreport reused ids, and one order can have several attempts when the buyer cancels and tries again.</li>
  <li><strong>Let the status API decide.</strong> A redirect to your return URL, or a "success" from a mobile SDK, can be forged, replayed or reversed later. Only a server-to-server status call (or, for CyberSource, a valid HMAC on the response) proves payment, and only when its amount and order id match what you stored.</li>
  <li><strong>Fulfil exactly once.</strong> The return URL, a webhook and the reconcile job can all report the same payment at the same moment. Each one moves the attempt only if its status is still the one it read, so exactly one wins, and only that one ships the order.</li>
  <li><strong>Run a reconcile job.</strong> Some buyers pay and close the tab, and most gateways send no webhook. A job running every 1 to 5 minutes re-checks attempts still open after two minutes, settles the paid ones, and marks expired the ones the gateway still doesn't know after its session window.</li>
</ol>

The guarded update behind step 4 is one SQL statement:

```sql
UPDATE payment_attempts
   SET status = 'paid', updated_at = now()
 WHERE id = $1 AND status = $2   -- the status this handler read
RETURNING *;
```

If it returns no row, another handler already moved the attempt and its write stands. Two more rules keep the money honest. A "paid" whose amount differs from yours goes to `unknown` and waits for a human. A gateway timeout or 5xx leaves the attempt alone (the page shows "We're confirming your payment"); it never marks the payment failed.

<Note type="warn" title="The redirect is not a payment">
  Anyone can type your return URL into a browser, so an order marked paid from the redirect's query string can be faked for free. The status API is the only proof.
</Note>

### Same routes for every gateway

Each guide below builds the same app: `POST /pay/{orderId}` starts a payment, `/pay/return/{attemptId}` confirms it, and the reconcile job re-checks open attempts. The routes never name a gateway. They call `startPayment` and `confirmPayment` on a gateway module, so adding Khalti to an eSewa checkout, or Fonepay to both, means writing one new module and keeping the routes. NEPALPAY QR is the one exception: it has no redirect, so its guide swaps the return route for a status route that the QR page polls.

### Webhooks and refunds by gateway

| Gateway | Server-to-server notification | Refunds |
|---|---|---|
| eSewa | ePay v2: none. Intent: signed JSON POST to `callback_url` | No refund API; refunds show up in the status API |
| Khalti | None in KPG-2 | Merchant refund API, or the dashboard |
| Fonepay | Web: none. Dynamic QR: WebSocket push | No public refund API; merchant panel or your bank |
| NEPALPAY QR | Confirm-payment POST (signed, Basic auth) if you register one with NCHL; WebSocket for live status | Through your acquiring bank |
| connectIPS | None | Not in the gateway API |
| CyberSource | Signed POST to the Merchant POST URL for every decision | REST API |
| NPS OnePG | Unsigned GET to the Notification URL | Not covered by my reference |
| IME Pay | None | Not covered by my reference |

Treat every notification as a hint: verify its signature if it has one, then call the status API and run the same guarded update. The full version, with the schema, the state machine and the go-live checklist, is in the [architecture guide](/docs/guides/architecture/). For apps, the [mobile guide](/docs/guides/mobile/) covers WebView and deep link patterns for Flutter, React Native, Android and iOS.
